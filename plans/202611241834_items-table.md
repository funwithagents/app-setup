# Items table: one table of what each section needs, with an action per line

**Status:** Done

Implements the updated [specs/ui.md](../specs/ui.md) ("The panels": the table, a line's action, the statuses) and [specs/app.md](../specs/app.md) (`SetupItem.variable`). Follows [202611241810_draft-and-saved.md](202611241810_draft-and-saved.md) in the same branch: the key saved from its line re-checks every tab through the `SecretStore.revision` that plan added. Leaves the contract unchanged: a key item is recognized by the variable it names.

## Scope

- `src/app_setup/app.py` — `SetupItem.variable`: the variable a key item is about, from the section's `x-secret-env` fields
- `src/app_setup/ui/report.py` — `item_status(item, progress) -> (status, explanation)`: ✅ Ready, ❌ Missing – required, 🟡 Missing – optional, ❔ Can't tell, and the transient ⏳ Installing… / Waiting / Preparing… 40% and ❌ Failed; `Progress` told an install from a preparation and a queued install; the summary line in the same words
- `src/app_setup/ui/panels.py` — the table (a header, a line per item of fixed-scale columns inside the section's `gr.render`); `_Installs`, one install at a time, shared by every tab like `_Preparations`, each line's install its own run with uv's latest line; **Install** on an extra's line, a password field and **Save** on a missing key's line, **Prepare** as before; **Install all** in one run through the same queue; the section checked again after a successful install or a key saved
- `src/app_setup/ui/form.py` — the hint for a section whose library is missing names **Install all**
- `tests/test_app.py`, `tests/ui/test_report.py`, `tests/ui/test_panels.py`, `tests-e2e/test_panels_in_browser.py` — as listed in each spec's Testing, the installer faked

## Steps

1. `SetupItem.variable` and its test.
2. The wording: statuses, explanations, transient states, the summary; their tests.
3. `_Installs`: queue, per-line run, Install all as one run; tests with a fake installer that waits on a gate.
4. The table drawn from a function the section's `gr.render` calls (so a test draws it in a page and calls its handlers): header, lines, actions; the rows timer's existing listener updating each line's status, explanation and button.
5. Browser tests: install from a line (installer, host extras and requirement status faked), save a key from its line; the earlier ones on the new wording.
6. Robustness found by the browser tests under load: the panels' renders in one concurrency group, the form not drawn before the draft is loaded, the table drawn again only when a check finds other items (a line being clicked is not replaced by an identical one).
7. Specs back to `Implemented` (files and index), both plans `Done`.
